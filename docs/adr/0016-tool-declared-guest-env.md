# ADR-0016: Tool-declared guest env and the precedence rule that makes it safe

## Status

Accepted. Implementation decision for [agent-vm #119](https://github.com/gregwebs/agent-vm/issues/119), a follow-up split out of [#82](https://github.com/gregwebs/agent-vm/issues/82). Extends [ADR-0015](0015-config-driven-tools.md) (the shipped catalog and a user's own file are parsed through the same raw→validated path) and [ADR-0002](0002-mirror-host-home-and-username.md) (the guest mirrors the host identity). Builds on the terms **Tool** and **Credential provider** in [CONTEXT.md](../../CONTEXT.md).

## Context

Before #119 `CODEX_HOME=/agent-vm-state/codex` was a generic constant (`credential_provider::GENERIC_GUEST_ENV`) applied to *every* launch. It names codex-the-tool's config dir, not a credential subsystem, so it belonged on the resolved tool. #82 gave us `config::Tool`, so #119 moves it there.

That makes `env` a **user-writable** field (a user or project `config.toml` may declare it), so the change is not just bookkeeping: it needs a rule for what a declared pair may and may not do.

The mechanics that the rule rests on:

- `SandboxBuilder::env` **appends** to a `Vec<EnvVar>` serialized as a JSON *array* (`vendor/microsandbox/sdk/rust/lib/sandbox/builder.rs`).
- The SDK's `merge_env_pairs` dedupes image env against user env but keeps duplicates **within** the user list.
- agentd applies the array with `cmd.env(key, val)` in a loop (`vendor/microsandbox/crates/agentd/lib/session.rs`), which is a map insert — so **the last occurrence wins**.

Emission position therefore has a safety meaning, not just a cosmetic one.

## Decision

- **Tool-declared guest env is published first (weakest).** `run::launch` emits `tool.guest_env()` right after the root-mode `.patch()` block, before `PATH`, the guest identity, `GUEST_ALWAYS_ENV` (`IS_SANDBOX`, `LANG`) and the provider-owned pairs. Because the guest applies the array last-wins, a project config that names `PATH`, `IS_SANDBOX`, `LANG` or a provider's variable is **overridden by the launcher**, not honoured.
- **Emission position is the control for every variable the launcher publishes unconditionally.** `PATH`, `IS_SANDBOX` and `LANG` are published on every launch, so position genuinely protects them and they stay **out** of the rejection set. `E2c` pins that they are always published (root mode included); as long as it holds, the rejection set does not need to grow for the keys `E2c` pins, and if someone makes one of them conditional, `E2c` fails and forces the choice — restore the unconditional emission, or extend the rejection set — into the open rather than letting it rot silently. There is also a third, deliberately unguarded class: `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` (`run.rs`) are published *host-conditionally* — only when already set and non-empty on the host — so when the host lacks them a tool declaration of the same name reaches `execve` unopposed, covered by neither position nor `check_env_key`. That is accepted, because the same declaration that sets `env` already sets `command` and `args`, so it can already run arbitrary guest code: there is nothing left to escalate.
- **`HOME`/`USER`/`LOGNAME` are rejected at the config seam, unconditionally.** The identity triple has a single producer, `user::guest_identity_env`, and it runs **only in non-root mode** (`user::resolve_guest_identity` returns `None` under `--root`). So under `--root` a tool declaration of those keys would win, and would also suppress agentd's passwd-derived `/root` fallback (`session.rs`'s `default_home_dir` returns early when exec env already contains `HOME`), silently breaking the root-mode credential symlinks. Validation cannot be mode-aware — `config` is parsed long before `run` computes `root_mode`, and the module deliberately knows nothing about launch — so the rejection is unconditional. It costs nothing legitimate: in non-root mode such a declaration was inert anyway. Diagnostic: `env key "HOME": must not be declared by a tool (agent-vm owns the guest identity environment)`. Pinned by `V2c` and `E2b`.
- **`MSB_` is rejected at the config seam too.** The vendored SDK rejects the prefix anyway (`SandboxBuilder::env` stashes the error, re-checked at `build()`), but it surfaces as a late `preparing sandbox config: …` with no file and no declaration index. One prefix owned by one vendor is not a deny-list; the seam check only buys the better diagnostic. Pinned by `V2b`.
- **`TERM` is deliberately left overridable.** The SDK injects `TERM=<default>` only when absent and only for TTY sessions, agent-vm never publishes `TERM`, and `TERM` selects terminal rendering — not an identity, a filesystem path, or a credential location. A tool that wants `TERM=dumb` is a legitimate use. Do not add it to the rejection set.
- **`env` is a `BTreeMap<String, String>`.** Key-sorted iteration is the emission order and the order definition equality compares, which keeps the emitted JSON deterministic for the goldens and makes version/conflict comparison order-insensitive. `env` is the **last** field in the `Tool` struct, the last `ToolField` variant, and the last `doctor` row suffix, so the fixed-order conflict warnings keep their ordering.
- **Diagnostics are value-safe.** A validation error names the `env` **key** (a variable name, escaped by `quoted_str`) and never a value, because a value may be a credential a user pasted; `doctor` renders only the count (`; env=N`, and only when `N > 0`).

## Consequences

- **`CODEX_HOME` is now declared by the `codex` and `shell` tools only.** A `claude`, `opencode` or `copilot` guest no longer sees it. That is the point of the ticket; it is not the always-on credential-capture change tracked in [#118](https://github.com/gregwebs/agent-vm/issues/118), which this ADR does not touch — the codex state dir, `codex/auth.json` and `codex/config.toml` are still provisioned on every launch.
- **`shell` keeps `CODEX_HOME`.** `shell` already declares `credentials = ["openai", …]`, so a shell launch already provisions the codex state dir and `codex/auth.json`; and codex has **no** `~/.codex` symlink by design (a symlink would shadow its `packages/` install prefix), so there is no fallback path. Dropping only the pointer would leave a fully-provisioned, unreachable credential and a silently signed-out hand-run `codex`. Pinned by `V5` and `E1`. The other three agents never read `CODEX_HOME`.
- **Upgrade note.** A user who shadows `codex` **or `shell`** in `~/.config/agent-vm/config.toml` (or a project `.agent-vm/config.toml`) loses `CODEX_HOME` on upgrade, because a user definition wins wholesale and does not inherit the shipped `env` — and for `shell` this silently signs out a hand-run `codex` inside the guest. `USAGE.md` carries an explicit "Upgrading:" note telling them to add `env = { CODEX_HOME = "/agent-vm-state/codex" }`.
- **`GENERIC_GUEST_ENV`, `GuestEnvSlot`, `GUEST_ENV_SLOTS` and the test-only `guest_env` are deleted.** "Guest env owned by no provider and applying to every launch" already has a home: `run::GUEST_ALWAYS_ENV`. The replacement, `credential_provider::provider_guest_env`, is a de-`match`ed *rename* of the old `guest_env_slot(ProviderOwned, …)`, not a new seam; it keeps `ProviderSpec::guest_env` and `Scope::applies` private to the module.
- **The tool-field list now lives in three places** — `config.rs`'s module doc, `USAGE.md`'s schema, and `CONTEXT.md`'s **Tool** entry — and they must stay in sync.
- **Forward compatibility is not provided.** A config written with the new `env` field hard-errors on an older binary (`RawTool` is `deny_unknown_fields`), the same as every field added since #80.

## Alternatives

- **Keep `GENERIC_GUEST_ENV` and empty it.** Rejected: an empty const plus a two-variant enum with one live arm is dead machinery, and it duplicates `run::GUEST_ALWAYS_ENV`.
- **Validate `env` keys against a compiled-in reserved set of *all* launcher-owned keys.** Rejected: an exhaustive list would have to be kept in sync by hand with four emission sites (two in `run.rs`, one in `user.rs`, one in the SDK) and would rot; it also adds a `config` → `run` dependency the module header forbids. Rejecting only the identity triple (single producer, already a fixed tuple) plus the one vendored prefix avoids all of that.
- **Document the root-mode hole and pin it with a test, instead of closing it.** Rejected by the user: a documented "at your own risk" key that silently breaks credential resolution is worse than a validation error, and the closed form costs no legitimate declaration.
- **Populate `Tool.env` only from the embedded `default-tools.toml`, not from `RawTool`.** Rejected: it would be the first asymmetry in #82/ADR-0015's single raw→validated path — a `Tool` field no user config could set — and it would need a second, hidden construction route the merge machinery must special-case. The general field is chosen; the cost is the validation and documentation recorded here.
- **A `GuestEnvVar { key, value }` newtype instead of a `BTreeMap`.** Rejected: a map's key and value are already positionally distinguished and unswappable, so the newtype would be a hand-rolled ordered map re-deriving the sorted, deterministic order `BTreeMap` gives for free. `HomeLink` is not precedent — it maps between two *different* namespaces where a swap is semantically meaningful.
